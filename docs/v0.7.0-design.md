# OpenKCM v0.7.0 — coordinated L1/L4 + account-scope cut

Implementation design + live progress tracker for the coordinated cut covering
[showroom#216](https://github.com/apeirora/showroom/issues/216) and
[showroom#217](https://github.com/apeirora/showroom/issues/217) under epic
[showroom#155](https://github.com/apeirora/showroom/issues/155).

## Context

Two open stories evolve OpenKCM beyond the L1/L2/L3 MVP currently live on cc-d2:

- **#216** adds the **L1 root-key family** (`AWSRootKey`, `AzureRootKey`,
  `OpenBaoRootKey`, plus stub kinds `GCPRootKey`, `VaultRootKey`, `HSMRootKey`)
  and **L4 `DataEncryptionKey`**. Also reshapes the schema across every
  kind: `tenantRef → tenantNameRef`, polymorphic
  `primaryRootKeyRef`/`fallbackRootKeyRefs` on `DomainKey`, a six-value
  `cryptoState.lifecycleState`, and a new common status surface
  (`operationId`, `reconciliationStatus`).

- **#217** collapses OpenKCM to a **single account-scoped APIExport**
  (`operations.openkcm.io`), moves `Tenant` from `governance.openkcm.io` into
  that group, retires `OrgBootstrapReconciler` together with the
  `governance.openkcm.io` APIBinding admin gesture and the
  `--field-manager=openkcm-bootstrap` SSA gesture, and reduces onboarding to
  a one-click marketplace install per account. The marketplace-created
  `operations.openkcm.io` APIBinding is the bootstrap trigger; init-agent is
  not used for this cut.

Both touch the same schemas and the same `tenantRef` field — they ship as
**one coordinated cut as `showroom-msp-openkcm v0.7.0`**. Every CRD,
controller, chart, mock-API and UI change lands in the same tag; cc-d2 is
torn down and reinstalled clean (no migration webhook).

Intended outcome: one marketplace install at an account workspace creates the
`operations.openkcm.io` APIBinding, the controller reacts to that APIBinding,
and the account receives a `Tenant` automatically. The customer then registers
their KMS backend (L1 Root Key) and creates an L2 DomainKey from the OpenKCM
UI, after which they can mint L3 ServiceKeys and L4 DataEncryptionKeys. The UI
renders each tier and a single-line trust-chain header sourced from sibling
resources.

### v0.7.3 design correction — Tenant-only auto-bootstrap

v0.7.0–v0.7.2 also auto-created a default `DomainKey` pre-wired to
`OpenBaoRootKey/<account>-root`. Treating the mock API as a real implementation
makes that wrong:

- **RootKey selection is a customer decision.** AWS / Azure / OpenBao depend
  on which KMS the customer actually has. The controller cannot invent the
  endpoint, auth config, or key name.
- **DomainKey type and root-key linkage are customer decisions.** Pre-creating
  a `Team` DomainKey pointing at a hypothetical `<account>-root` forces both
  a type and a provider before the customer has had a chance to configure
  either, and leaves the DomainKey permanently `RootKeyResolutionFailed` if
  the customer chooses any other path.

v0.7.3 narrows `AccountBootstrapReconciler` to **Tenant only**, and the UI
gains explicit creation flows for Root Keys (provider picker for AWS / Azure /
OpenBao with per-provider auth fields) and Domain Keys (type picker, Active
Root Key picker). See Phase 2 + Phase 6 status.

### Contradictions resolved

- **Tenant apiGroup**: the OpenKCM team's `tenant.yaml` uses
  `governance.openkcm.io/v1alpha1`, but #217 explicitly directs the move
  to `operations.openkcm.io` and points out the other six samples already
  use that group. The sample's `apiVersion` line was treated as stale.
  **Decision: Tenant lives under `operations.openkcm.io/v1alpha1`** in v0.7.0.
- **`ServiceKey.spec.activate`**: not in the sample. Dropped. Lifecycle
  now driven entirely by mock-API endpoints across the six-value enum.
- **Reference shapes**: `tenantNameRef` / `domainKeyRef` / `serviceKeyRef`
  are plain strings (same-namespace, same-group, name-only). Only
  `primaryRootKeyRef` / `fallbackRootKeyRefs[]` stay polymorphic
  `{apiGroup, kind, name}` structs because L1 polymorphism requires them.
- **`identityInfo.certificateSecretRef`**: three fields `{name, namespace, key}`
  — modelled as `shared.SecretKeyReference` (not `corev1.LocalObjectReference`)
  to keep the data-key selector.
- **L1 stub kinds**: `GCPRootKey`, `VaultRootKey`, `HSMRootKey` ship as
  CRD + Go types only. No reconcilers in v0.7.0. Present so that
  `primaryRootKeyRef` accepts them; controllers come later.
- **Bootstrap trigger**: `APIBinding` creation is the trigger. The controller
  watches account-workspace APIBindings and bootstraps only when the
  `operations.openkcm.io` binding appears. No `InitTarget`, `InitTemplate`,
  init-agent chart, or init-agent host deployment is required for closing
  #216/#217.
- **Tenant identity**: Tenant is account-level. Security remains path-derived,
  but the canonical identity is the account segment from
  `root:orgs:<org>:<account>`, not the org segment and not the user-controlled
  `spec.tenantNameRef`.

### Phase 2 — Controllers ✅

- `internal/controller/governance/` deleted.
- `internal/controller/operations/` now houses 8 reconcilers:
  - `AccountBootstrapReconciler` — watches `APIBinding` objects in account
    workspaces, filters for the `operations.openkcm.io` binding, and then
    idempotently creates a `Tenant` CR in the account workspace. It replaces
    OrgBootstrap and is the only bootstrap mechanism for #217. **v0.7.3:** the
    DomainKey auto-creation was removed; RootKey and DomainKey are now
    user-driven (see UI Phase 6).
  - `TenantReconciler` (operations) — migrates Tenant logic to the new
    group, status surface, drops the `ensureInitTarget` no-op.
  - `DomainKeyReconciler` — new schema; resolves polymorphic
    `primaryRootKeyRef` via `rootkey.go` GVK helper and requires the L1 root
    key to be `Active` before provisioning L2; path-derived tenant identity
    preserved per `showroom#203`, but must derive the account segment because
    Tenant is now account-level.
  - `ServiceKeyReconciler` — plain-string `domainKeyRef`; lifecycle
    driven by mock-API state (no `spec.activate`).
  - `AWSRootKeyReconciler`, `AzureRootKeyReconciler`,
    `OpenBaoRootKeyReconciler` — register with mock API,
    surface `identityInfo`, drive `Ready` + `cryptoState`.
  - `DataEncryptionKeyReconciler` — waits on parent ServiceKey to reach
    `Active` before provisioning the DEK.
- `rootkey.go` — GVK + factory map for the six L1 kinds.
- `cmd/main.go` — rewritten: single operations APIExport, all 8
  reconcilers wired, governance manager + flag dropped.
- `internal/openkcmapi/client.go` extended with `CreateRootKey`/`GetRootKey`/
  `DeleteRootKey`, `CreateDEK`/`GetDEK`/`DeleteDEK`,
  `SuspendKey`/`DestroyKey`/`CompromiseKey`.
- Test files updated to new schema.
- Account-level path resolution is enforced across Tenant, DomainKey,
  ServiceKey, real L1 root keys, and DataEncryptionKey; advisory
  `spec.tenantNameRef` is ignored for security-sensitive identity.
- Unit coverage added for account path parsing, APIBinding filtering, and
  default Tenant + DomainKey bootstrap resources.
- **Verification**: `make test` clean.
